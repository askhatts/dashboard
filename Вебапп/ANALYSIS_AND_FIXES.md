# 🔍 ПОЛНЫЙ АНАЛИЗ ПРИЛОЖЕНИЯ: Дашборд скрининга Абайской области

## 📋 О ЧЁМ ЭТО ПРИЛОЖЕНИЕ

### Назначение
Веб-приложение на R Shiny для мониторинга и анализа программ онкологического скрининга в Абайской области Казахстана. Охватывает два вида скрининга: рак молочной железы (РМЖ) и колоректальный рак (КРР).

### Основные функции
1. **Импорт данных** из Excel-файлов с автоматическим нечётким сопоставлением медицинских организаций
2. **ГИС-визуализация** — интерактивные карты с маркерами МО и хороплетами районов
3. **Аналитика** — графики динамики, сравнение МО и районов, таблицы данных
4. **Эпидемиологический мониторинг** — заболеваемость, смертность, стадийность, выживаемость по районам

### Архитектура
- **SQLite** база данных с 8 таблицами (справочники, детальные данные, агрегаты, эпидемиология)
- **launcher.R** — консольное меню для выбора режима работы
- **01_setup_database.R** — создание БД из шейп-файлов
- **data_import_app.R** — Shiny-приложение для импорта данных
- **app.R** — главный дашборд визуализации
- **app_functions.R** — вспомогательные функции (агрегация, карты, графики)

## 🐛 НАЙДЕННЫЕ ОШИБКИ

### КРИТИЧЕСКИЕ (приложение не работает или теряет данные)

#### 1. Утечка соединений с БД в app.R (строки 164, 323-325)
```r
# ПРОБЛЕМА: conn() создаёт НОВОЕ соединение при каждом вызове reactive
conn <- reactive({ dbConnect(SQLite(), "data/abai_region.sqlite") })
```
Каждый вызов `conn()` открывает новое соединение, которое никогда не закрывается. При активном использовании это приведёт к сотням открытых соединений и блокировке SQLite.

**Исправление:** Использовать `reactiveVal` с одним соединением или pool.

#### 2. Отсутствие пересчёта агрегатов после импорта (data_import_app.R, строка 365)
Импорт скрининга вставляет детальные данные, но **не вызывает `calculate_aggregates()`**. Карты и графики работают с агрегатами → данные не появятся на дашборде.

#### 3. Импорт вставляет только 3 поля из ~30 (data_import_app.R, строки 348-356)
```r
INSERT INTO %s (mo_id, start_date, start_year, start_month)
VALUES (...)
```
Из 30+ полей (возраст, BI-RADS, диагнозы, биопсия и т.д.) в БД попадают только `mo_id`, `start_date`, `start_year`, `start_month`. Все остальные данные теряются.

#### 4. SQL-инъекции через sprintf с пользовательскими данными
В `01_setup_database.R` (строка 307) и `data_import_app.R` (строки 397-427):
```r
sprintf("WHERE district_name_ru LIKE '%%%s%%'", district_name)
```
Если название содержит одинарную кавычку (есть в реальных названиях МО), запрос падает с ошибкой. Используется `gsub("'", "''", ...)` частично, но не везде.

#### 5. Конфликт имён input-элементов (data_import_app.R)
`screening_type` используется и в data_import_app.R (строка 89), и в app.R (строка 65) — одинаковый inputId, что создаёт конфликт при возможном merge.
`cancer_type` аналогично (строка 160 vs строка 76).

### СЕРЬЁЗНЫЕ (функционал работает неправильно)

#### 6. Месяцы отображаются на английском (app.R, строка 176)
```r
choices = c("Все" = "all", setNames(1:12, month.name))
```
`month.name` — английские названия (January, February...). Для русскоязычного приложения нужны русские.

#### 7. Координаты МО = центроиды районов (01_setup_database.R, строки 396-398)
Все МО одного района получают одинаковые координаты (центр полигона района). На карте 16 МО Семея будут наложены друг на друга в одной точке.

#### 8. Агрегация не считает BI-RADS, checklist_findings и другие поля (app_functions.R, строки 27-41)
`calculate_aggregates()` для РМЖ считает только: total_started, total_completed, total_refusals, total_expired, cancer_count, biopsy_count. Пропущены: birads_m0-m3, birads_m4_m5, checklist_findings, diagnosis_findings, benign_count — всё, что определено в схеме `screening_breast_aggregated`.

#### 9. Расчётные показатели (detection_rate, ppv, coverage_percent) нигде не вычисляются
Таблица `screening_breast_aggregated` содержит поля `detection_rate`, `ppv`, `coverage_percent`, но `calculate_aggregates()` не заполняет их. На карте они всегда будут NULL/0.

#### 10. Нет валидации year как integer в create_screening_map (app_functions.R, строка 110)
`input$filter_year` приходит как character из selectInput. `sprintf("WHERE data_year = %d", year)` может упасть с ошибкой.

#### 11. Эпидемиология: INSERT OR REPLACE не работает корректно (data_import_app.R, строки 418-427)
`INSERT OR REPLACE` при UNIQUE constraint удаляет старую запись и вставляет новую, но вставляет только `incidence_count` и `mortality_count`. Все остальные поля (early_stage_percent, five_year_survival и т.д.) теряются, даже если были сопоставлены.

#### 12. area_km2 считается в WGS84 (01_setup_database.R, строка 300)
```r
area_km2 <- as.numeric(st_area(row$geometry)) / 1e6
```
`st_area()` для WGS84 (4326) выдаёт результат в градусах², а не в м². Нужно преобразовать в метрическую проекцию или использовать `st_area()` с `s2` геометрией.

### УМЕРЕННЫЕ (UX проблемы и неоптимальности)

#### 13. Построчный импорт вместо batch insert (data_import_app.R, строки 315-359)
Цикл `for (i in 1:nrow(import_data))` с отдельным `dbExecute` на каждую строку. При 10000 записей это ~10000 SQL запросов, что занимает минуты вместо секунд.

#### 14. Нет транзакции при импорте
Если ошибка на строке 5000 из 10000, первые 5000 уже в базе, а остальные нет. Нет `dbBegin/dbCommit/dbRollback`.

#### 15. Hardcoded путь setwd (launcher.R, строка 5)
```r
setwd("F:/Сделано/Аналитика/Вебапп")
```
Работает только на конкретном компьютере. Лучше определять путь относительно скрипта.

#### 16. Нет обновления координат МО в табе "Координаты" (data_import_app.R)
Кнопка `load_coords` не имеет observeEvent handler. Функционал координат не реализован.

#### 17. Карта эпидемиологии не фильтрует по месяцу
`create_epi_map()` принимает только `year` и `cancer_type`, игнорируя месяц.

#### 18. Колонки screening table в app.R показывают одинаковые поля для РМЖ и КРР
```r
s.total_started as Начато, s.cancer_count as Рак
```
Для КРР должны быть hemoccult_positive, colonoscopy_total и т.д.

## 🚀 ПУТИ ОПТИМИЗАЦИИ

### Производительность
1. **Connection pooling** — использовать `pool` пакет вместо `reactive(dbConnect(...))`.
2. **Batch INSERT** — `dbWriteTable(..., append=TRUE)` вместо построчных вставок (ускорение в 50-100x).
3. **Prepared statements** — `dbSendQuery()` с параметрами вместо `sprintf()`.
4. **Ленивая загрузка** — не загружать все данные при старте, а запрашивать по мере необходимости.

### Надёжность
5. **Параметризованные запросы** — защита от SQL-инъекций.
6. **Транзакции** — `dbWithTransaction()` для всех операций записи.
7. **Валидация входных данных** — проверка типов, диапазонов, обязательных полей.
8. **Логирование** — запись операций в import_log таблицу.

### UX
9. **Автоматическое определение колонок** — fuzzy matching по названиям колонок Excel.
10. **Прогресс-бар** с реальным прогрессом при импорте.
11. **Русские названия месяцев** в фильтрах.
12. **Скачивание данных** из таблиц в Excel.
13. **Разброс координат** МО внутри района для визуальной читаемости.
